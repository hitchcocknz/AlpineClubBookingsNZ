## Summary

- Save a changed central-server address, delete its previous key and reset its answers in one transaction under the existing settings row lock. Key replacement and disconnect use the same protocol.
- Every outbound request captures its address, uncached key and credential identity under that fence, then releases it before HTTP. Materialise the singleton before locking for first-time setup.

## Security And Privacy Impact

- Prevents sending the previous central server's bearer key to a newly saved address. Existing Full Admin destination/key gates stay in place; response and audit payloads remain free of key material. Operational reads bypass stale process-local credential caches.

## Data Integrity Impact

- Address movement, credential deletion and both answer resets commit or roll back together. Credential writes/deletes retain the encrypted store's transactional audit and cache invalidation. Version recording continues to compare the captured address/credential identity after HTTP.

## Concurrency And Lock Impact

- Writer class(es), canonical lock key(s), and acquisition order: Singleton connection configuration and request capture, disjoint from money/capacity cohorts (INV-LOCK-001). Existing `lockServerNzSettings` locks `ServerNzSettings.id = SERVERNZ_SETTINGS_ID` with FOR UPDATE; order is settings row, credential row, credential audit (INV-LOCK-002). No new advisory key or raw lock statement; row-lock inventory updated (INV-LOCK-003). All shared settings transactions use the canonical SERVERNZ_TRANSACTION_OPTIONS budget (150s timeout, 10s maxWait).
- Immutable pre-lock key source and mutable under-lock re-read: SERVERNZ_SETTINGS_ID defines the immutable singleton id in servernz-settings.ts. createMany(skipDuplicates) materialises an absent row, then the existing row lock is acquired. Settings route re-reads the old address under it; request capture re-reads the settings and stored encrypted credential through the same transaction client. No provider cache participates in that read.
- Status-guarded claim and proof that a lost claim runs no side effect: No lifecycle/status claim is introduced; replacement is serialised by the singleton row lock. The address comparison is made under lock and an unchanged normalised address preserves the key. Delete/reset failures roll back all staged writes. The existing version recorder still drops a mismatching captured identity without recording a response. HTTP starts only after request capture commits.
- Relevant open/last-10 PR numbers, counterpart writers/tests, and compatibility evidence: Open #4277 was read, including its download recorder and API/settings changes; it shares the same settings-row lock and settings-before-credential order. Current-main first-parent last ten touching this subsystem: #4438, #3985, #3831, #3608, #3516, #3480, #3370, #3091, #2949, #2530 (git history inspected; public PR file/patch inspection also covered #4438/#3985/#3516/#3091/#2949 and related #3457/#3446). Existing recorder reads the credential version under the same settings fence; other settings writers acquire no credential row, so cannot invert the order. There is no new outbox/lifecycle transition. Version/late-answer, sync/cursor, credential-store, lock inventory and writer census tests pass; real PostgreSQL interleavings await host execution. #4277 may need a textual merge reconciliation in servernz-settings.ts/servernz-api.ts; retain this fence and its transaction-client reads when integrating.
- Provider calls inside a transaction (write `None`, or justify the bounded exception from `docs/CONCURRENCY_AND_LOCKING.md`): None. Requests use the captured connection after the transaction ends; response recording remains a separate fenced transaction.
