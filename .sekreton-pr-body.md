## Summary

- A central-server version answer is now recorded only for the connection it came from. Each request captures its identity before the HTTP call: the stored base URL plus the API key's durable credential version (`credentialVersionOf`, a hash of the stored row, which gets a fresh IV on every write). The plaintext key is never part of it.
- `recordServerVersionIfCurrent` (new, `src/lib/servernz-version-record.ts`) runs after the HTTP call in one short transaction:
  - it takes the `ServerNzSettings` row lock (`lockServerNzSettings`, the #4277 protocol);
  - it re-reads the base URL and the credential version under that lock;
  - it records only if both still match the captured identity.
- A mismatch records nothing. That covers key reuse (A -> B -> A), a key replaced or removed, and a base-URL change.
- Both writers go through it: `refreshStoredServerVersion` (and `fetchServerVersion`'s connection) and the 409 `API_VERSION_MISMATCH` refusal path.
- Unchanged:
  - version normalisation (`storableServerVersion`);
  - the failure policy (a failed check records nothing and never pauses; a received answer that cannot be recorded throws);
  - the caller's pause on a 409.
- A refused answer also drops this process's cached ServerNZ credential, so the next request resolves and checks the stored key rather than reusing a stale cached one for the rest of the 45 s window.
- `getOperationalServerNzApiKey` is replaced by `getOperationalServerNzCredential`, which returns the key and its version from one row. `readIntegrationCredentialVersion` is added as an uncached version re-read through the caller's client; it never decrypts.
- `recordServerVersionCheck` no longer has a default client, and a census pins its one caller.

## Security And Privacy Impact

- Less of the plaintext key moves through the code: the late-answer check no longer compares or holds a second decrypted copy. The connection identity carries only the stored address and a SHA-256 version token of the encrypted row.
- The key is still never logged or audited.
- The new log line says only that an answer was dropped, with the two version numbers.

## Data Integrity Impact

- `ServerNzSettings.serverVersion` can no longer describe a connection it did not come from.
- Before: a late answer after a key change or address move, or after A -> B -> A (where the old plaintext comparison passed), could overwrite the forget and wrongly pause or un-pause syncing until the next check.
- Now such an answer is refused under the row lock, and the next request checks the stored connection inline.

- Writer class(es), canonical lock key(s), and acquisition order: the version recorder (`recordServerVersionIfCurrent`) is a singleton-settings writer.
  - Its one lock is the `ServerNzSettings` row: `SELECT 1 FROM "ServerNzSettings" WHERE "id" = 'default' FOR UPDATE` via `lockServerNzSettings`, the #4277 download-fence protocol.
  - It takes no advisory lock and adds no key. No other lock is taken, so there is no ordering to compose.
  - It is disjoint from the booking/capacity/credit and settlement clusters. The site is registered in `ROW_LOCK_SITE_INVENTORY` and documented in `docs/CONCURRENCY_AND_LOCKING.md`.
- Immutable pre-lock key source and mutable under-lock re-read: the key is the constant singleton id `SERVERNZ_SETTINGS_ID`.
  - Before the HTTP call, the request captures its identity: `ServerNzSettings.baseUrl` as stored, and `credentialVersionOf` the API-key row its bearer token was decrypted from (one read).
  - Under the lock, the recorder re-reads `baseUrl` and the credential version uncached (`readServerNzCredentialVersion`, never decrypted) and compares both.
- Status-guarded claim and proof that a lost claim runs no side effect: the guard is the identity comparison under the row lock. A mismatch returns `false` before `recordServerVersionCheck`, so nothing is written, and the caller only logs.
  - The one side effect after a refusal is dropping this process's in-memory credential cache, which is idempotent and writes nothing.
  - Proven by the gate suite (`not.toHaveBeenCalled` on every mismatch case), by the realdb forced race (the recorder queued on the row, then `false` with the column still null), and by the mutation checks listed above.
- Relevant open/last-10 PR numbers, counterpart writers/tests, and compatibility evidence: #4277 (open; download fence) introduces the same `lockServerNzSettings`.
