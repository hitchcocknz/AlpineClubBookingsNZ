## Summary

- **Roles.** A pure, declarative statement builder (`src/lib/database-roles.ts`) and an operator CLI (`pnpm run db:provision-roles`). The CLI is a dry run unless given `--apply`. It provisions three roles. The migration role (`tac_migrator`) owns every object in schema `public`. The application role (`tac_app`) gets SELECT, INSERT, UPDATE and DELETE on ordinary tables. On `BookingLedgerLine` and `AuditLog` it gets **only INSERT and SELECT**, and on `_prisma_migrations` only SELECT. The audit-retention role (`tac_audit_retention`) gets SELECT and DELETE on `AuditLog`, plus UPDATE of `ipAddress` and `userAgent` only. The operator stays the existing superuser and is used only by people.
- **One transaction, and it is idempotent.** The run creates or repairs the roles and strips every role membership. It hands ownership of tables, views, sequences, types and routines to the migration role, skipping extension members. It revokes, then grants back, and sets `ALTER DEFAULT PRIVILEGES FOR ROLE <migrator>` so tables that future migrations create reach the application at once. Finally it re-checks the result with the server's own privilege functions and **raises, rolling everything back**, if the application role could still change an append-only row. It also raises if any role holds a superuser-class attribute or can `SET ROLE` to a wider role, or if the retention role holds any other right.
- **Audit retention.** `runAuditLogRetentionJob` maintains `AuditLog` through a client built from the optional `AUDIT_RETENTION_DATABASE_URL`. Unset, it uses the application client as before. The archive client and the retention client are built by one helper, with the same adapter and the same `PRISMA_CLIENT_GLOBAL_OMIT`. The anonymised columns come from one list, which the role's column-scoped UPDATE grant is built from too. The archive database's role is unchanged.
- **Compose.** `APP_DB_USER`/`APP_DB_PASSWORD` set the credentials for both web slots and the cron leader, and `MIGRATION_DB_USER`/`MIGRATION_DB_PASSWORD` for the `migrate` service. Each falls back to `tac`/`DB_PASSWORD`. With them unset, the rendered stack is **byte-identical** (checked with `docker compose config`). Pool sizes and the migration lock timeout are untouched. The deploy script's URL-safety check now covers the two new passwords.
- **Writer census.** The only application or cron code that UPDATEs or DELETEs an audit or ledger table is the three `AuditLog` writers in `audit-retention.ts`. No triggers or functions touch those tables (see Data Integrity). `pnpm run audit:census` reports `non-producing DML: 3`, all of them in `audit-retention.ts`. Migrations' `AuditLog` DML runs as the owning migration role.
- Production connection strings are **not** switched: that step belongs to the owner. The docs give the blue/green switch-over, the staging rehearsal and the rollback.

## Security And Privacy Impact

- With the roles split, the application's credential cannot UPDATE, DELETE or TRUNCATE the booking ledger or the audit log. It also cannot lock their rows, alter the schema, `SET ROLE`, or run superuser-only statements (proven against PostgreSQL). Only the narrow retention role can anonymise or delete audit rows, and it holds no other right. With the split, the 3 `superuser_reserved_connections` slots really are kept for the operator.
- No auth or billing behaviour changes. Nothing changes until an operator sets the new variables. Passwords are never printed: the dry run shows placeholders, and the CLI never echoes its statements.
- The AI Diagnostics role is unchanged, and the realdb test compares its privileges before and after. Its builder's role-creation and membership-strip statements moved into shared exports, and its statement list is byte-identical (checked by comparing old and new output).

## Data Integrity Impact

- With the split, the database refuses to rewrite append-only facts. Two limits are documented, not changed. Migrations run as the table owner. `BookingLedgerLine.bookingId` has `ON DELETE CASCADE`, and the cascade runs with the owner's rights, so deleting a booking still removes its lines.

## Migration Or Deployment Impact

- No Prisma migration. Roles are cluster state that holds secrets, so they come from the operator CLI, like the AI Diagnostics role (ADR-007).
- Blue/green: provisioning does not affect the live colour, which still connects as `tac`. Setting `APP_DB_USER`, `MIGRATION_DB_USER` and `AUDIT_RETENTION_DATABASE_URL` and then deploying switches the `migrate` service and the new colour. The old colour keeps its superuser connection until it is stopped, and no grant it relies on is removed. Rollback is to unset the variables and deploy. `docs/BLUE_GREEN_MIGRATION_POLICY.md` → "Which role a migration runs as" keeps every migration readable by the deployed old code. Migrations must not add GRANTs or REVOKEs, must not need a superuser, and a new append-only relation is declared in code, followed by a re-provision.
- Pool budget: the audit-retention pool is 2, only while the nightly job runs and only once the split is adopted. That makes the worst case 29 of 40 (`DEPLOYMENT.md` → "Connection pool sizing").
