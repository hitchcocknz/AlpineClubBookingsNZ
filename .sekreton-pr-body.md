## Summary

A stale browser tab could pay ask A after replacement ask B was sized but before B saved its cancellation of A. B then asked for A's balance again. Every carrying-ask queue now re-reads the live balance under its global and Payment row locks before writing B or cancelling A. A changed balance refuses the queue; ordinary recovery re-plans using the existing sizing helper.

The same boundary covers ordinary edits, financial-review charges, currency reissues, reduction reissues and recovery replay. A frozen legacy replay cannot reconstruct its own versus carried amount, so it refuses after any captured additional ledger row on every retry; the existing exhaustion alert asks officers to reconcile the unpaid balance. Provider calls run after or before the transaction. Invoice documentation no longer lists this capture window as a kept superseded capture.

## Concurrency And Lock Impact

- Writer class(es), canonical lock key(s), and acquisition order: Settlement-money writers, Tier 2 (`INV-LOCK-001`); existing `pg_advisory_xact_lock(1)` first, then `lockPaymentForRefundedTotal` on the Payment row, then any recovery-row claim (`INV-LOCK-002`). The shared `lockAdditionalAskQueue` site is registered in `GLOBAL_LOCK_SITE_REGISTRY` (`INV-LOCK-003`). No advisory key is introduced and no capacity tier changes.
- Immutable pre-lock key source and mutable under-lock re-read: Payment id from the existing mint/recovery context; after locking, read `additionalAmountCents` and `additionalPaymentStatus` through the transaction client and compare the same outstanding-balance rule used at sizing. No module-client read is used under the queue locks (`INV-LOCK-004`).
- Status-guarded claim and proof that a lost claim runs no side effect: Recovery holds its PROCESSING claim with the expected processing timestamp before its callback; a lost claim runs no queue writes or cancellations. Inline queues throw `CarriedAskChangedError` before any replacement row or cancellation is written. Refusal unit tests assert the write callback never runs; realdb cases assert no replacement ledger row or cancel of A exists. A retry with its own row resumes post-write work instead of mistaking itself for a later edit.
